# Coding Agent Benchmark 知识大纲

SWE-bench 及其切片在第一章。切片只在该章末尾简要说明。Terminal-Bench 原版和 Terminal-Bench 2 各自一章。其余 benchmark 仍各自一章。

两个词先固定，后面每章都用它们：

- **评测 harness**：出题方的环境、隐藏测试和打分程序。
- **Agent scaffold**：模型外面的循环和工具。benchmark 不附送工具时，工具属于 scaffold。

带 `[核对]` 的数字在论文、仓库和榜之间不一致，引用前以该 benchmark 的官方页面为准。

## SWE-bench

### 它问的问题

给定一个真实仓库在 `base_commit` 的样子，以及对应的 GitHub issue 文本，交出一份补丁，使问题行为被修好，且无关功能的测试仍然通过。

做对不等于复现金补丁。金补丁是当时人类 PR 里、去掉测试改动之后的参考实现。另一份写法只要让规定的测试过渡成立，也算 resolved。官方 issue 讨论里明确过：测试和金补丁不能拿来生成答案；只允许使用 `base_commit` 的代码和 issue 描述。

题目从已合并、并且能关联到 issue 的 PR 里挖。原始全集集中在 12 个流行 Python 仓库。关联方式是在 PR 标题、正文和提交说明里找 “fixes / closes / resolves #编号” 这一类引用。

### 一道题的字段，以及谁能看见

列只有两列：解题时、评测时。

| 字段 | 是什么 | 解题时 | 评测时 |
| --- | --- | --- | --- |
| `instance_id` | 通常是 `owner__repo-PR号` | 可见 | 可见 |
| `repo` | GitHub 仓库 | 可见 | 可见 |
| `base_commit` | 修复 PR 落上去之前的提交 | 可见，作为代码起点 | 容器从这里开始 |
| `problem_statement` | issue 标题加正文。多条 issue 会拼在一起 | 可见，这是任务说明 | 不参与打分 |
| `hints_text` | PR 首次提交之前的评论，里面可能有解法暗示 | 数据集里有；论文主实验不用 | 不用 |
| `patch` | 金补丁，PR 中的非测试改动 | 不可见 | 仅在 `--predictions_path gold` 时当作待测补丁 |
| `test_patch` | PR 中新增或修改的测试 | 不可见 | 先打进仓库，再跑测试 |
| `FAIL_TO_PASS` | 打上测试后、打上修复前会失败，修复后应通过的测试名 | 不可见 | 决定「问题有没有被解决」 |
| `PASS_TO_PASS` | 修复前后都应该通过的测试名 | 不可见 | 决定「有没有打坏原有行为」 |
| `FAIL_TO_FAIL` / `PASS_TO_FAIL` | 其他过渡，用于附加统计 | 不可见 | 默认可选，不决定 resolved |

`problem_statement` 的收集范围是 issue 正文，加上 PR 首次提交之前、挂在这些 issue 上的评论。`hints_text` 来自更早的 PR 讨论。二者不要混。

### 这些测试名是怎么来的

造题时，出题方自己把仓库跑两遍（概念上）：

- 只有 `base_commit` 加上 `test_patch`：新测试失败，旧测试通过。
- 再加上金补丁：那些失败测试变绿，旧测试仍然通过。

从这两次日志里得到 `FAIL_TO_PASS` 和 `PASS_TO_PASS`。所以「标准答案」是一组测试状态过渡，不是一个字符串 diff。

过滤大致要求：PR 真的改了测试；仓库能安装、测试能跑；FAIL_TO_PASS 非空；行为稳定，不是时好时坏的 flaky。具体过滤脚本随版本变化。这里只写目的，不抄脚本。

### 评测 harness 的流程

官方模块是 `swebench.harness`。常用入口：

- 构建或拉取镜像
- `run_evaluation`：读一份预测文件，逐题打分
- 事后 `report`：只根据已经落下的日志重新汇总，不再开容器

预测文件是 JSONL。每行至少有 `instance_id` 和模型补丁（unified diff）。`predictions_path` 设为 `gold` 时，用参考补丁做自检，用来确认镜像和测试本身是通的。

单题打分顺序：

1. 准备这道题的容器，代码在 `base_commit`。
2. 把模型补丁放进容器，尝试 `git apply`。官方实现会换几种 apply 参数；一次失败可能弄脏工作区，所以会先把树恢复干净再试下一种。若命令退出码非零，还会用反向检查判断补丁是不是其实已经完整打上。
3. 打不上则该题失败，记为无法应用补丁，不再冒充「测试没过」。
4. 跑该仓库的评测脚本。脚本负责应用 `test_patch`、执行测试、留下日志。多模态题还会把数据集里另存的图片资源放回测试期望的路径，因为文本形式的 `test_patch` 带不走二进制基线。
5. 用该仓库的日志解析器，把每条测试标成通过、失败或错误。
6. 对照 `FAIL_TO_PASS` 与 `PASS_TO_PASS` 判 resolved。
7. 写出该题日志和本次 `run_id` 的汇总。

`[核对]` 模型补丁与 `test_patch` 的先后以当前 `run_evaluation` 为准。教学表述用上面的顺序：harness 先应用模型补丁，仓库评测脚本再应用测试补丁并跑测试。若两者改到同一处，顺序会影响能否应用。

判分规则（默认 PASS_AND_FAIL 这一类）：

- `FAIL_TO_PASS` 里每一个测试都要通过，问题才算被解决。
- `PASS_TO_PASS` 里每一个测试都要保持通过，才算没有回归。
- 两者同时成立，该题 resolved。
- 主指标是 resolved 的题目比例。

`[核对]` 日志里完全没有出现的测试名，在不同 grading 版本里可能算通过（代码注释里出现过 silent success）或算失败。缺失、错误、跳过是否等于失败，以所用 harness 版本的 `grading.py` 为准，并在报告里注明版本。

结果缓存按 `run_id` + `instance_id`，不看补丁内容。同一 run、同一题第二次会直接复用第一次的结果。换了一份补丁必须换 `run_id`。

其他运行事实：

- 并行度 `max_workers` 过高会因抢资源变慢。文档建议低于大约 `min(0.75 * CPU 数, 24)`。
- 每题有超时。
- 平台建议 x86_64；arm64 支持是实验性的，Apple Silicon 上常见做法是把镜像命名空间留空、在本地构建。
- 日志分镜像构建和评测运行两类。汇总在该 `run_id` 的结果文件里。

### 解题时的工具：benchmark 不发，scaffold 发

用同一张表讲完。

| 做法 | 模型能做什么 | 循环 | 用途 |
| --- | --- | --- | --- |
| 论文里的 Oracle 检索 | 直接看到金补丁改过的文件，一次写出补丁 | 无 | 上限参照，不是真实 agent |
| 论文里的 BM25 检索 | 用 issue 文本检索若干文件，一次写出补丁 | 无 | 早期非 agent 基线 |
| SWE-agent 的 ACI | 窗口看文件、有界搜索、按行编辑、编辑后做语法检查，不过则回滚；用 submit 交卷 | 多步 | 说明「给模型的电脑界面」本身会改变分数 |
| mini-swe-agent | 只有 bash。不依赖模型的 tool-calling 接口。每一步是一次独立命令执行，而不是一条一直活着的 shell 会话 | 多步 | 官方 Bash Only 榜：500 道 Verified，所有模型套同一个 scaffold，用来比模型 |
| Agentless | 先定位文件，再生成补丁，再用回归测试在候选补丁里挑 | 固定流水线 | 说明不一定要自由 ReAct 才能做这道题 |
| OpenHands 等 CodeAct | bash、Python、文件编辑，更接近通用编程 agent | 多步 | 研究系统和产品原型常用 |
| 厂商 agent | 各自的编辑、搜索、终端，有的还有浏览器和子 agent | 多步，预算各不相同 | 产品公告里的数字。不能和 Bash Only 直接横比 |

ACI 里后来被证明有用的界面决定，讲设计理由，不讲成「唯一正确工具集」：

- 文件查看一次给大约 100 行，并提供上下滚动和文件内搜索，避免整文件灌进上下文。
- 全库搜索只列出「哪些文件命中」，不把每处上下文都展开。
- 编辑命令带 linter；语法不合法就不要让这次编辑生效。
- 命令没有输出时，也要明确回报「成功且无输出」，避免模型把空白当成失败。

Bash Only 视图现在是 swebench.com 上 Verified 的默认比较方式：环境固定为 mini-swe-agent，比的是模型在同一界面下的表现。厂商如果用自己的 agent 再跑一遍 Verified，那是另一个实验。

解题时的合法能力边界：

- 可以读 `base_commit` 上已有的代码和测试，可以自己写临时测试，可以跑仓库里当时就存在的命令。
- 不可以拿到 `test_patch`、`FAIL_TO_PASS`、`PASS_TO_PASS` 和金补丁。官方隐藏测试是交卷之后才注入的。
- 因此「模型自己跑了仓库里的旧测试」不等于「它看见了判分测试」。很多判分测试是 PR 新加的，在 `base_commit` 上还不存在。

### 端到端时序

分成造题、解题、打分三段。

**造题（离线，出题方做一次）**

1. 从仓库里找「issue 被某个 PR 关掉」的样本。
2. 拆成非测试改动（金补丁）和测试改动（`test_patch`）。
3. 做成可复现环境，在「只有测试」和「测试加金补丁」两种状态下跑测试。
4. 记下 FAIL_TO_PASS 与 PASS_TO_PASS。丢掉装不上、测不稳、测试与问题对不上的样本。

**解题（每个模型和 scaffold 做一次）**

1. 容器或工作区停在 `base_commit`。
2. 模型只拿到 `problem_statement` 和这个代码树。
3. scaffold 按自己的工具循环行动。
4. 抽出 `git diff`，写成预测 JSONL 的一行。

**打分（评测 harness，每个预测文件做一次）**

1. 换一个干净容器，仍然从 `base_commit` 开始。解题过程中的现场不能留下来。
2. 应用模型补丁；应用失败则该题未解决。
3. 应用 `test_patch` 并跑测试。
4. 解析日志，对照两组测试名。
5. 汇总 resolved 比例。报告里同时写数据集、scaffold、超时、日期、harness 版本。

第 2 步和第 3 步必须隔离。否则模型可以在现场把测试改掉，或留下解题时才安装的状态，评测就不再是在判那份补丁。

### 论文设定和后来的 agent 设定

SWE-bench 发布时并不是今天这种多步 agent 榜。

- 2023 论文的主实验是检索加一次生成，不是多步工具循环。Oracle 检索把金补丁碰到的文件直接给模型，BM25 则是真实检索。
- 2024 起，SWE-agent 这一类多步 scaffold 成为主要报告方式，评测也改为全容器。
- 再往后，榜单分裂成「固定 bash scaffold 比模型」和「各家 agent 比产品」。

### 走一遍：教学例 `acme__ports-17`

下面的仓库、issue 和测试都是为了把字段走通而写的缩小例子。字段名、预测文件和评测入口对齐公开格式。它不是 SWE-bench 榜上的某一道真题，也没有对应的官方镜像。

**1. 模型在解题时看见的**

起点代码停在 `base_commit`。issue 是任务说明。

```python
# ports.py，位于 base_commit
def parse_port(text: str) -> int:
    port = int(text)
    if port <= 0 or port > 65535:
        raise ValueError("port out of range")
    return port
```

```text
parse_port rejects port 0

Calling parse_port("0") raises ValueError.
Port 0 is a valid port number and should be returned.
Ports above 65535 must still be rejected.
```

仓库里已经有两道旧测试：`test_port_80` 期望 80 被接受，`test_port_too_high` 期望 70000 被拒绝。模型可以读到它们，也可以自己再跑。此时还没有 `test_port_zero`，因为那道测试在后来的 PR 里才加进去。

**2. 出题方把人类 PR 拆成两份 diff**

金补丁只留行为修改。测试改动单独成为 `test_patch`。解题时这两份都不可见。

```diff
# patch：金补丁
diff --git a/ports.py b/ports.py
--- a/ports.py
+++ b/ports.py
@@ -1,6 +1,6 @@
 def parse_port(text: str) -> int:
     port = int(text)
-    if port <= 0 or port > 65535:
+    if port < 0 or port > 65535:
         raise ValueError("port out of range")
     return port
```

```diff
# test_patch
diff --git a/tests/test_ports.py b/tests/test_ports.py
--- a/tests/test_ports.py
+++ b/tests/test_ports.py
@@ -6,3 +6,6 @@ def test_port_too_high():
     with pytest.raises(ValueError):
         parse_port("70000")
+
+def test_port_zero():
+    assert parse_port("0") == 0
```

**3. 两遍测试日志变成名单**

出题方先只打上 `test_patch`，再打上金补丁，各跑一次。

```text
只有 test_patch
FAILED tests/test_ports.py::test_port_zero
PASSED tests/test_ports.py::test_port_80
PASSED tests/test_ports.py::test_port_too_high

test_patch 加上金补丁
PASSED tests/test_ports.py::test_port_zero
PASSED tests/test_ports.py::test_port_80
PASSED tests/test_ports.py::test_port_too_high
```

于是：

- `FAIL_TO_PASS` = `test_port_zero`。它记录「问题有没有被修好」。
- `PASS_TO_PASS` = `test_port_80` 和 `test_port_too_high`。它们记录「旧行为还在不在」。

数据集里这两个字段有时是 JSON 数组，有时是数组的字符串。评测前都会解析成测试名列表。

**4. 另一份补丁也可以 resolved**

模型交卷时不需要复述金补丁。下面这份把条件写成区间，diff 文本和人类 PR 不同，但三道测试的过渡相同，这道题仍然 resolved。

```diff
diff --git a/ports.py b/ports.py
--- a/ports.py
+++ b/ports.py
@@ -1,6 +1,6 @@
 def parse_port(text: str) -> int:
     port = int(text)
-    if port <= 0 or port > 65535:
+    if not (0 <= port <= 65535):
         raise ValueError("port out of range")
     return port
```

若模型把上界检查删掉，`test_port_zero` 会通过，`test_port_too_high` 会失败。FAIL_TO_PASS 全过并不足够，PASS_TO_PASS 有一条失败，resolved 为 false。

若 unified diff 的上下文对不上 `base_commit`，harness 记为补丁没有应用。这和「测试跑了但没过」是两种日志。空补丁同样 unresolved：报告里能看到补丁缺失。

**5. 预测文件和评测入口**

scaffold 结束时抽出 git diff，写成 JSONL 的一行。官方字段是 `instance_id`、`model_name_or_path`、`model_patch`。

```json
{"instance_id":"acme__ports-17","model_name_or_path":"demo-model","model_patch":"diff --git a/ports.py b/ports.py\n..."}
```

打分入口（参数名来自当前 `swebench.harness.run_evaluation` 文档）：

```bash
python -m swebench.harness.run_evaluation \
  --dataset_name princeton-nlp/SWE-bench_Lite \
  --predictions_path preds.jsonl \
  --max_workers 4 \
  --run_id ports-demo-001
```

`predictions_path gold` 时，待测补丁换成数据集里的金补丁，用来确认镜像和测试本身能通。那是自检，不是模型成绩。

单题容器从 `base_commit` 重新开始。镜像大致三层：基础语言镜像、这个仓库的依赖镜像、停在该提交的题目镜像。harness 把 `model_patch` 写进容器，按几种 `git apply` 尝试打上。某一次失败可能把工作区弄脏，所以下一次尝试前会先恢复干净树。几种方式都没有成功时，再用反向检查看补丁是不是其实已经完整打上。仍然没有，这题就停在「无法应用」。

应用成功后，该仓库的评测脚本再打上 `test_patch`、跑测试、留下日志。解析器把每条测试标成通过、失败或错误。默认规则下，FAIL_TO_PASS 全部通过且 PASS_TO_PASS 全部保持通过，报告里 `resolved` 为 true。

```json
{
  "acme__ports-17": {
    "patch_exists": true,
    "patch_successfully_applied": true,
    "resolved": true
  }
}
```

同一 `run_id` 加同一个 `instance_id` 会复用已有日志，缓存不看补丁内容。换了一份 `model_patch` 就要换 `run_id`。

主指标是本次预测文件里 resolved 为 true 的题目比例。报告同时写数据集、scaffold、超时和 harness 版本。Lite 上的比例、Verified 上的比例、Bash Only 上的比例是三次实验。

### 分支

下面这些都沿用本章的题型：交一份补丁，在干净容器里看 FAIL_TO_PASS 与 PASS_TO_PASS。差别在题从哪来、解题时多看见什么、以及榜单是否把 scaffold 写死。数字带 `[核对]`，以 swebench.com 或对应论文为准。

**Full。** 原始测试集，约 2294 道，12 个 Python 仓库。本章前面写的流程就是这一套。

**Lite。** 约 300 道，从 Full 抽出的子集，方便改 scaffold 时少跑容器。字段、可见性和判分都不变。Lite 上的比例不能写成 Full 或 Verified。

**Verified。** 约 500 道。人看过问题陈述和 FAIL_TO_PASS，陈述说不清、或测试太窄、太宽、和 issue 对不上的会被拿掉。多名标注者里有一人认为严重就剔除，所以它不是随机抽样，也不表示题更简单。判分规则与 Full 相同。题和金补丁长期公开。

**Bash Only。** 题就是 Verified 这 500 道。所有模型用同一个 mini-swe-agent，唯一动作是 bash，每步是一次独立命令，而不是一条一直活着的 shell。打分仍是本章的 harness。厂商自己的 agent 再跑一遍 Verified，不是这一列。

**Multimodal。** issue 里带截图或界面图，解题时可见。文本形式的 `test_patch` 带不走的图片基线，评测时要放回容器。不能读图的 scaffold 看到的题目是残缺的。`[核对]` 榜上约 517；FAQ 里的开发集约 100，且有的评测走 API。两个数字不要合成一个。

**Multilingual。** 官方多语言切片。`[核对]` 约 300 道、42 个仓库、9 种语言。判分哲学相同，日志解析按语言和测试框架分开。不要和 Multi-SWE-bench 或 SWE-PolyBench 当成同一题库。

**Pro。** 更长的改动，公开材料里平均大约一百行、约四个文件。解题时除了问题陈述，还有人写的需求列表，以及可选的接口说明；它们规定行为，不规定实现。公开集和保留集偏向强 copyleft 仓库，商业集是私有代码、只公布分数。`[核对]` 1865 = 731 + 858 + 276。测试仍是人工看过的 FAIL_TO_PASS / PASS_TO_PASS。公开集可以落成 Harbor 任务目录来跑，判的还是补丁加隐藏测试。三个子集的分数分开报。

**Live。** 用持续出现的新 issue 降低整库被背下来的可能。环境由 RepoLaunch 自动做 Docker，并多次重跑以确认测试过渡稳定。lite / verified 切分可以冻结，full 按月追加，报告要写截止到哪个月。另有多语言和 Windows 切分；Windows 题在 PowerShell 环境里打分。`[核对]` 论文快照约 1319 道、93 个仓库，不是永久规模。

## Terminal-Bench

### 它问的问题

给 agent 一台为这道题准备好的 Linux 机器和一段自然语言指令，让它把机器做成指令描述的状态。指令可以是编译、配服务、修复损坏的数据、跑完一段流程。没有 GitHub issue，也没有一份事先存在的失败测试当作完成定义。

这一章只写原版 Terminal-Bench。目录格式和打分方式在下一代 Harbor 里换过，那是下一章，两代的通过率不能写在一起。

### 一道题的字段，以及谁能看见

| 字段或路径 | 是什么 | 解题时 | 评测时 |
| --- | --- | --- | --- |
| `task.yaml` 里的指令 | 任务说明，嵌在配置里 | 可见 | 不参与文本匹配 |
| `task.yaml` 其余项 | 超时、资源、解析器名称 | 运行配置 | 决定怎么读测试输出 |
| 根目录上的 Dockerfile | agent 的工作容器 | 生活在其中 | 被检查的那台机器 |
| `run-tests.sh` | 验证入口，常见是跑 pytest | 不可见 | agent 结束后执行 |
| `tests/` | 测试与期望数据 | 不可见 | 随验证脚本运行 |
| `solution.sh` | 参考解 | 不可见 | 用来确认题本身可解 |

### 标签怎样造出来

题目是人工编写并核对的，不是从 PR 里挖出来的。一道题要同时有能构建的镜像、足够决定目标的指令、一份能让测试通过的参考解，以及 agent 在工作容器里看不到的测试和期望数据。

### 评测 harness 的流程

1. 用 Dockerfile 拉起容器，把指令交给接入的 agent。
2. agent 在超时内任意执行命令、改文件、起进程。
3. agent 停止或超时后，在同一环境里跑 `run-tests.sh`。
4. 测试命令的退出码和标准输出交给 Terminal-Bench 仓库里的解析器，映射成通过或失败。解析器不属于单道题，而属于评测框架。
5. 汇总通过率。被计分的是 agent 加模型，不是裸模型。

原版没有要求任务自己写奖励文件。成功与否由框架根据 pytest 一类命令的结果决定。

### 解题时的工具

框架提供的是容器和停止后的验证时机，不规定编辑器。接入 Terminus 一类中立 scaffold 时，模型面对的是 shell。接入厂商 CLI 时，还会带上那家自己的搜索、编辑和重试。同模型换 scaffold，或只换 CPU、内存和时长，分数都会变。

解题时能看见每条命令的输出。看不见 `run-tests.sh`、期望数据和参考解。

### 端到端时序

造题：写 `task.yaml`、Dockerfile、测试和 `solution.sh`，并确认参考解能通过框架解析器。

解题：agent 改这台机器，直到自己停或超时。

打分：跑 `run-tests.sh`，用仓库内解析器得到二元结果。答案是结束时的环境，不是一份 git diff，也不是命令历史文本。

### 走一遍：教学例 `summarize`

同一道终端题会在下一章用 Harbor 格式再写一遍。这里只使用原版目录。脚本、数据和超时都是教学例，不是 Terminal-Bench 仓库里的某道真题。

原版一道题通常长这样：

```text
summarize/
  task.yaml
  Dockerfile
  run-tests.sh
  solution.sh
  tests/test_outputs.py
```

很多真题还有 `docker-compose.yaml`。教学例只用 Dockerfile，用来看清谁在什么时候读哪个文件。

`task.yaml` 把指令和解析器名字放在一起。真实任务还会写作者、难度和各类超时；下面只留和流程有关的字段，超时数字是示例。

```yaml
instruction: |-
  /app/bin/summarize.sh should print how many lines are in
  /app/data/notes.txt. Print one integer and nothing else.
  The script currently fails.
parser_name: pytest
max_agent_timeout_sec: 300
max_test_timeout_sec: 60
```

工作容器里有一份坏掉的脚本和一份数据。agent 看得到它们，也看得到自己每条命令的输出。

```dockerfile
FROM python:3.11-slim
WORKDIR /app
RUN mkdir -p /app/bin /app/data
RUN printf 'alpha\nbeta\ngamma\n' > /app/data/notes.txt
RUN printf '#!/bin/bash\nwc -l /app/data/missing.txt\n' > /app/bin/summarize.sh
RUN chmod +x /app/bin/summarize.sh
```

`notes.txt` 有 3 行。指令已经要求打印行数，所以 agent 可以自己数。它看不到的是验收脚本：框架在 agent 停止之后才把 `tests/` 和 `run-tests.sh` 放进环境。

```python
# tests/test_outputs.py
import subprocess

def test_line_count():
    out = subprocess.check_output(["/app/bin/summarize.sh"], text=True)
    assert out.strip() == "3"
```

```bash
#!/bin/bash
# run-tests.sh
pytest -q /tests/test_outputs.py
```

`parser_name: pytest` 指向 Terminal-Bench 仓库里的解析器，不是这道题自带的。解析器读 pytest 的输出，映射成通过或失败。原版不要求任务自己写 `reward.txt`。

参考解 `solution.sh` 只给 oracle 用，用来确认题本身能通过这个解析器。一种能通过的写法是把行数单独打出来：

```bash
#!/bin/bash
wc -l < /app/data/notes.txt | awk '{print $1}'
```

agent 若改成 `printf '3\n'`，这道教学测试也会通过，因为验收只看标准输出。指令若还要求「脚本必须读取 notes.txt」，测试就应该覆盖那个行为；测试没写到的行为，原版解析器不会额外判。计分对象是接入的 agent 加模型。换 scaffold、CPU、内存或超时，就是另一次实验。

### 和 SWE-bench 的差别

SWE-bench 从固定 commit 抽出补丁，在干净容器里重放。原版 Terminal-Bench 从空任务容器开始，认的是 agent 离开后的那台机器。完成与否由框架解析测试输出，而不是 FAIL_TO_PASS 名单。

## Terminal-Bench 2

### 它问的问题

和上一章是同一类事：按自然语言指令把一台机器做到目标状态。这一章写的是 Terminal-Bench 2 以及它使用的 Harbor 任务格式。2.0 与 2.1 的通过率不要和原版 `task.yaml` 的结果混报。

`[核对]` 公开讨论里 2.0 / 2.1 约 89 道人工题，论文进入 ICLR 2026。题量以对应版本的官方仓库为准。题少，单题权重大，报告要带重复次数。

### 一道题的字段，以及谁能看见

| 字段或路径 | 是什么 | 解题时 | 评测时 |
| --- | --- | --- | --- |
| `instruction.md` | 任务说明，单独一个文件 | 可见 | 不参与打分文本 |
| `task.toml` | 超时、资源、要导出的 artifacts | 运行配置 | 约束验证器能读什么 |
| `environment/` | Dockerfile 或 compose | agent 生活在这里 | 被改过的现场 |
| `tests/test.sh` | 验证脚本 | 不可见 | agent 结束后运行 |
| `tests/` 其余文件 | pytest、期望数据 | 不可见，不要放进 environment | 验证器可读 |
| `solution/solve.sh` | 参考解 | 不可见 | 只用来做 oracle，不和模型答案比文本 |
| 奖励文件 | `/logs/verifier/reward.txt` 或 `reward.json` | 不可见 | 脚本必须写下 |

### 标签怎样造出来

仍然是人工题，不是 PR 挖掘。一道题成立的条件和原版相同：环境能建、指令足够、参考解能通过、测试对 agent 不可见。通过与否改成任务自己把奖励写进文件，而不再由框架仓库里的解析器解释 pytest 输出。

### 评测 harness 的流程

1. 按 `environment/` 拉起 agent 容器，只提供 `instruction.md`。
2. agent 在 `task.toml` 的超时和资源上限内改这台机器。
3. 结束后运行 `tests/test.sh`。验证器可以在另一个容器里，只读取任务声明导出的 artifacts、烤进验证镜像的文件，或 compose 里的持久边车。这样 agent 无法在自己的容器里改掉测试。
4. 脚本把奖励写成一个数字，或一个多指标 JSON。主榜常用 0 和 1。也可以是浮点或部分得分，引用时要写明用的是哪一种。
5. 汇总通过率。单位仍是 agent 加模型。

Harbor 不再把「测试输出到二元奖励」的解析器放在框架仓库里。任务自己负责产生奖励文件。

### 解题时的工具

和原版一样，框架不发编辑器。中立 scaffold 给出 shell；厂商 agent 自带额外工具和重试。2.x 的资源限制写在 `task.toml` 里，换限制就是另一次实验。

模型看得见自己命令的输出，看不见 `tests/`、参考解和奖励文件该怎么写才算对。

### 端到端时序

造题：写 `instruction.md`、环境、`tests/test.sh` 和 `solve.sh`，用参考解确认奖励能到满分，并确认测试没有进 agent 镜像。

解题：agent 操作工作容器，直到停止或超时。

打分：导出 `task.toml` 允许留下的现场，在验证器里跑 `test.sh`，读奖励文件。不把 shell 历史当成提交物。

### 走一遍：同一道 `summarize`，换成 Harbor

第 2 代把上一章那道题拆成 Harbor 任务目录。指令、环境和验证不再挤在一个 YAML 里。

```text
summarize/
  instruction.md
  task.toml
  environment/Dockerfile
  solution/solve.sh
  tests/test.sh
  tests/test_outputs.py
```

`instruction.md` 就是给 agent 的正文，内容和上一章 `task.yaml` 里的 instruction 相同。配置进 `task.toml`。下面是流程相关的一小段；Harbor 的完整 schema 还有作者、网络策略、单独的验证环境等字段。

```toml
schema_version = "1.4"

[task]
name = "demo/summarize"
description = "Print the line count of notes.txt"

[verifier]
timeout_sec = 60.0

[agent]
timeout_sec = 300.0

[environment]
cpus = 1
memory_mb = 2048
storage_mb = 10240
```

`environment/Dockerfile` 与上一章相同：坏掉的 `summarize.sh` 和 3 行的 `notes.txt`。测试文件不要打进这张镜像。

Harbor 在验证阶段才把 `tests/` 复制到容器里的 `/tests`，并执行 `bash /tests/test.sh`。工作目录常常是 `/app`。脚本自己把奖励写成数字。Harbor 优先读 `/logs/verifier/reward.json`，没有再读 `reward.txt`。主榜常用 0 和 1。

```bash
#!/bin/bash
# tests/test.sh
pytest -q /tests/test_outputs.py
if [ $? -eq 0 ]; then
  echo 1 > /logs/verifier/reward.txt
else
  echo 0 > /logs/verifier/reward.txt
fi
```

`test_outputs.py` 仍断言标准输出去掉空白后是 `3`。参考解搬到 `solution/solve.sh`。Oracle 运行时才会把它复制到 `/solution` 并执行。agent 阶段没有这个目录。

默认验证器和 agent 共用结束后的那台容器，因此能看见 agent 改过的 `/app`。需要把验收代码完全隔开时，把验证器设成单独容器，只把任务声明导出的 artifacts 送进去。换了这种隔离方式，就是另一次实验。

一次运行的入口形状是：

```bash
harbor run -p summarize -a terminus-2 -m <model>
```

`-a` 是 scaffold，`-m` 是模型。通过率写成这一对的结果。原版 `task.yaml` 加解析器得到的通过率，和第 2 代 `reward.txt` 得到的通过率，不要写进同一个数。

### 和原版、和 SWE-bench 的差别

相对原版：指令从 `task.yaml` 拆到 `instruction.md`，环境放进 `environment/`，`run-tests.sh` 变成 `tests/test.sh`，退出码解析改成奖励文件，验证器可以和 agent 不在同一容器。

相对 SWE-bench：提交物仍是机器的最终状态或声明的 artifacts，不是 unified diff。测试在 agent 结束后才运行，不存在交卷前注入的 `test_patch`。打分前不会把现场丢掉再只重放一份补丁。

## LiveCodeBench

### 它问的问题

用竞赛网站上持续新增的题，考模型写程序、修程序、执行程序、预测测试输出。主场景仍是：读题面和样例，交出一份能通过隐藏测试的程序。没有仓库，没有跨文件历史。

抗污染是这套考试的设计中心：每题有公开的比赛日期，评新模型时可以只取训练截止日期之后的题。

### 一道题的字段，以及谁能看见

| 字段 | 是什么 | 解题时 | 评测时 |
| --- | --- | --- | --- |
| 题面 | 自然语言，含约束和样例 | 可见 | 不参与比对 |
| 样例输入输出 | 题面的一部分 | 可见 | 通常不作为唯一判分依据 |
| 平台与题目编号 | LeetCode、AtCoder 或 Codeforces | 可见 | 用来追溯 |
| `contest_date` | 比赛或题目发布日期 | 不需要给模型 | 用来切时间窗 |
| 隐藏测试 | 完整输入输出或 checker | 不可见 | 执行模型程序 |
| 时间与内存限制 | 平台限制 | 可见（题面里） | 执行时强制 |
| 参考解 | 平台上的正确做法 | 不可见 | 不要求文本相同 |

### 标签怎样造出来

题目来自三家平台的定期比赛，经过大量人类选手过滤，题面和判定相对干净。收集时带上发布日期。判定器沿 APPS 的 checker 改过，补上原先没覆盖的边界。另有精简测试集，用来加速估计，和全量测试集必须分开报告。`[核对]` 论文与仓库对题数、时间范围的说法会随版本增加。具体窗口以所用 release 为准。

### 评测 harness 的流程

1. 按场景组装提示：生成、自我修复、执行、或预测测试输出。
2. 采样一份或多份程序。标准设定没有工具循环。
3. 在沙箱里用隐藏测试执行。生成场景看输出是否被 checker 接受，并受时间、内存限制。
4. 自我修复：把失败信息再给模型，看后续程序能否通过。
5. 执行场景：给程序和输入，看模型预测的输出。测试输出预测：给测试输入，预测程序该打出什么。
6. 用 `contest_date` 过滤后再算分。不过滤的总分不能和「截止日期之后」的分比较。

### 解题时的工具

标准协议不提供仓库、搜索或 bash。模型一次或少数几次写出程序。若实验改成 agent 在容器里调试，那是另一套协议，必须另报，不能写进 LiveCodeBench 主榜。

### 端到端时序

造题：从比赛收集题面、样例、隐藏测试和日期。

解题：模型只看见题面（以及该场景额外允许的失败信息或程序文本）。

打分：沙箱执行 + checker。再按日期窗口重算。

### 变体

四个场景分开报：代码生成、自我修复、代码执行、测试输出预测。生成分高不代表后三个也高。全量测试与精简测试（lite / fast）分开报。时间窗本身也是一种切分。

### 和 SWE-bench 的差异

没有 `base_commit`，没有回归测试，判定是输入输出或 checker，不是 FAIL_TO_PASS。新鲜度靠新题，不靠把旧 PR 藏起来。分数对 scaffold 不敏感，因为标准协议几乎没有 scaffold；对采样次数、温度和时间窗敏感。

## Multi-SWE-bench

### 它问的问题

和 SWE-bench 相同的 issue resolving，但题目来自 Python 以外的仓库，用来看模型换语言之后还剩多少。论文覆盖 Java、TypeScript、JavaScript、Go、Rust、C、C++，有的版本把 Python 也算进八种语言。`[核对]` 题数存在 2132 与 1632 两套说法，外加一个 mini 切分。引用时绑定论文版本或仓库 commit。

### 一道题的字段，以及谁能看见

字段与 SWE-bench 同构：`instance_id`、仓库、`base_commit`、issue 文本、金补丁、测试补丁、FAIL_TO_PASS、PASS_TO_PASS。解题时只见 issue 和修复前代码。测试补丁和两组测试名在打分时使用。另有人工标注的难度和是否跨文件，用于分层报告，不作为给模型的提示。

### 标签怎样造出来

五段管道：按星标和可运行性选仓库；收集关联 issue 的 PR；从 CI 和文档抽出依赖，做成 Docker；在「只有测试」和「测试加修复」两种状态下跑，只留有清晰失败到通过、且无回归的 PR；专家双标、交叉复核。仓库说明里提到数十名标注者。难度分层来自这次人工标注，不是从 diff 行数自动算完就结束。

### 评测 harness 的流程

与 SWE-bench 相同的三步：干净环境回到 `base_commit`，打上模型补丁，注入测试再跑。预测文件仍是 JSONL 补丁。日志解析按语言和测试框架分别写，因为 pytest 的输出长得不像 JUnit、Go test 或 cargo。镜像按实例或仓库准备。官方入口在 multi-swe-bench 仓库，不直接复用 Python 版 `swebench` 命令的全部参数。

### 解题时的工具

benchmark 同样不发工具。论文同时报了 Agentless、SWE-agent、OpenHands。换语言之后，ACI 里假设「Python 语法检查器」的部分不一定仍适用，scaffold 要换成该语言的构建和测试命令。这一点要写进读分条件。

### 端到端时序

造题：多语言 PR → 容器 → 测试过渡 → 人工难度。解题：scaffold 在对应语言的仓库里改代码，交出 diff。打分：新容器重放 diff。跨文件题单独汇总，因为论文的主要发现之一是跨文件明显更难。

### 变体

完整集、mini、以及按语言和难度切开的报告。不要和 SWE-bench 官方 Multilingual（约 300 题、9 种语言、42 个仓库）合成一个名字。

### 和 SWE-bench 的差异

任务定义和判分哲学相同。不同的是语言、测试日志解析、人工难度标签，以及「Python 上的 scaffold 不能原样拿来比」。

## SWE-Gym

### 它问的问题

提供一批可执行的真实 Python issue，用来训练和比较软件工程 agent，而不是取代 SWE-bench 当唯一头条榜。任务形态仍是：读问题，改仓库，让失败测试变绿且不破坏原有测试。

### 一道题的字段，以及谁能看见

与 SWE-bench 同构。公开环境描述里：问题来自原始 issue 或 PR；代码在容器的 `/testbed`，停在对应 `base_commit`；FAIL_TO_PASS 与 PASS_TO_PASS 决定奖励。这两组测试名不是解题提示。`[核对]` 一份环境封装写的是 2438 道、11 个 Python 仓库，lite 为 230；缺镜像的题会被排除。以论文和数据集卡为准，不要和 SWE-bench 的 12 个测试仓库混成同一批题。

### 标签怎样造出来

从真实 PR 收集，并做成每题或每仓库可运行的镜像。保留条件与 SWE-bench 相同：存在稳定的失败到通过，且有回归测试。训练集的仓库选择会避开 SWE-bench 测试仓库，否则训练分没有意义。

### 评测 harness 的流程

打分复用 `swebench.harness` 的语义：抽出 git diff，在评测环境里跑测试，全部 FAIL_TO_PASS 通过且 PASS_TO_PASS 仍通过则奖励 1，否则 0。有的交互环境把这件事绑在 `answer` 动作上：模型调用提交后，环境才抽 diff 并打分，回合结束。离线评测则和 SWE-bench 一样读预测 JSONL。

### 解题时的工具

题目本身不附带唯一工具集。一份公开环境给了 bash、查看文件、按行插入、字符串替换、新建文件，以及结束用的 `answer`。这是该环境的接口，不是 SWE-Gym 论文规定的唯一 ACI。换一套工具要另报。资源描述里出现过每题 1 CPU、2 GB 内存这一类限制，引用训练曲线时要带上。

### 端到端时序

造题：真实 PR → 镜像 → 测试过渡。训练：agent 在沙箱里改代码，提交后得到 0/1。报告：在 SWE-Gym 自己的题上的解决率，和在 SWE-bench Verified 上的迁移解决率，是两个数字。

### 变体

all 与 lite。lite 用于更便宜的迭代。不要把在训练集上的解决率写成 Verified 分数。

### 和 SWE-bench 的差异

判分几乎相同。角色不同：SWE-Gym 是训练场和开发集，SWE-bench Verified 是对外考试。两者仓库重叠与否必须在实验里写明。

## SWE-smith

### 它问的问题

自动制造大量「可执行的 bug」，用来训练 agent。考试题仍然可以是 SWE-bench；SWE-smith 负责把训练数据的规模做上去。模型要修的是被注入进仓库的故障，问题陈述常常是事后生成的，不是当时 GitHub 上的那条 issue。

### 一道题的字段，以及谁能看见

| 字段 | 是什么 | 解题时 | 评测时 |
| --- | --- | --- | --- |
| 仓库与镜像 | 同一仓库的题共享一个环境，而不是每题一张巨大镜像 | 可见代码 | 打分起点 |
| bug 补丁 | 把正确代码改坏的 diff | 已经体现在工作区里 | 评测时工作区就是坏的 |
| 金补丁 | 把 bug 改回去的反向 diff | 不可见 | oracle |
| 生成的 issue 文本 | 另一个模型根据 bug 写出的问题说明 | 可见 | 不参与字符串匹配 |
| FAIL_TO_PASS | 注入前通过、注入后失败的原有测试 | 不可见 | 修复后应重新通过 |

### 标签怎样造出来

先让仓库在最新提交上能跑测试：用 agent 尝试安装，再人工确认，并要求八成以上既有测试通过。仓库来自 PyPI 高下载包里星标足够的项目，并排除 SWE-bench 那 12 个测试仓库。

然后用几种方式产生候选 bug：让模型改坏一个函数；只给函数签名和文档，让模型重写坏实现；对语法树做随机变换（删条件、改运算符等）；把真实 PR 反过来应用；把多个 bug 叠在一起。

验证：把候选补丁打进仓库，跑测试，只保留「至少弄坏一个原先通过的测试」的补丁。测试超过约两分钟的候选丢掉。通过之后，再用模型为这个 bug 写 issue 文本。

### 评测 harness 的流程

训练题用 SWE-smith 自己的验证和评测命令：应用预测补丁、跑该仓库测试、看那些被弄坏的测试是否恢复。超时单独设置。报告文件列出哪些 `instance_id` 被解决。

论文里模型好不好，主要仍看 SWE-bench Lite 和 Verified 的 resolved。因此 SWE-smith 有两套数字：合成题上的训练奖励，和真实考试上的迁移分数。

### 解题时的工具

造数据时用过 SWE-agent 做安装。训练和推理沿用 SWE-agent 或 mini-swe-agent 一类 scaffold，由实验决定。生成 issue 的模型不是解题模型，不能把「issue 是模型写的」理解成解题时能看见 bug 补丁。

### 端到端时序

造环境 → 生成候选 bug → 用测试过滤 → 生成问题文本 → agent 在坏仓库上修 → 用被弄坏的测试当奖励 → 再到 SWE-bench 上考迁移。

### 变体

按造 bug 的策略切开：LM 修改、LM 重写、语法树、PR 反向、组合。论文会比较哪种 bug 训出来的 agent 迁移更好。实例 ID 里通常带策略标记。

### 和 SWE-bench 的差异

SWE-bench 的 bug 是仓库历史上真的发生过的。SWE-smith 的 bug 是注入的，测试是仓库里原来就有的，问题文本是生成的。共享镜像降低了磁盘成本，也意味着环境不如「每题一张镜像」那么隔离。不要把合成题解决率直接写成 SWE-bench 分数。

## R2E-Gym

### 它问的问题

提供可执行的软件工程训练环境，并用在这些环境上训出来的 agent 去考 SWE-bench。单题仍是修一个可被测试判定的仓库问题。数据里既有从真实提交收集的，也有程序化合成的执行环境。

### 一道题的字段，以及谁能看见

解题可见：问题文本和带依赖的代码环境。不可见：隐藏测试和参考补丁。提交物是补丁。`[核对]` 环境总数以论文和 Hugging Face 数据集卡为准，公开材料里是数千量级，不要在未核对时写成精确整数。

### 标签怎样造出来

用执行结果过滤：候选修改必须让一组测试从通过变为失败，或符合真实 PR 的失败到通过。环境预装到可以跑测试。合成数据与真实数据在实验里应分开报，否则看不出增益来自哪里。

### 评测 harness 的流程

仓库自己的运行脚本负责在 R2E-Gym 或 SWE-bench Verified 上产生轨迹和补丁。脚本说明写明：这只生成补丁，最终分数要用 SWE-bench 官方 harness。因此 R2E-Gym 的对外分数如果写的是 Verified，判分规则就是 SWE-bench 那一套，不是另一套指标。

### 解题时的工具

编辑型 agent 有步数上限（公开示例里出现过 40 步）和是否使用函数调用的开关。具体工具是该 agent 的配置：编辑、执行命令等。换步数就换了考试。

### 端到端时序

造可执行环境 → 在环境里采样轨迹并过滤成功修复 → 监督或强化学习 → 在 Verified 上用官方 harness 打分。训练奖励和 Verified resolved 分列。

### 变体

合成子集、真实子集、以及专门为 Verified 评测准备的数据集镜像。步数和温度写进实验名。

### 和 SWE-bench 的差异

对外头条数字应是官方 harness 上的 Verified。R2E-Gym 自己的题是训练分布。把训练分布上的成功率放在 Verified 旁边而不加说明，是误读。

## Multi-SWE-RL

### 它问的问题

把 Multi-SWE-bench 那套管线做成可扩展的强化学习数据，而不是另一套排行榜。问题仍是多语言 issue resolving，奖励来自测试是否被修复。

### 一道题的字段，以及谁能看见

与 Multi-SWE-bench 相同的字段。解题不见测试补丁。`[核对]` 早期公开说明里有四千量级实例。以数据发布说明为准。

### 标签怎样造出来

沿用 Multi-SWE-bench 的五段管道，强调持续往里加可执行实例。每条数据要能在容器里算出 0/1 奖励，否则不能当 RL 样本。

### 评测 harness 的流程

训练时的奖励用该实例的测试过渡。对外报告如果引用 Multi-SWE-bench 或 SWE-bench 的 resolved，必须改用那些考试自己的 harness，不能用训练脚本里的近似奖励代替。

### 解题时的工具

由训练用的 agent 决定，常见是多语言下的 bash 或编辑动作。语言不同，同一套「跑测试」的命令就不同，奖励函数要跟仓库的测试入口走。

### 端到端时序

生产实例 → 容器里交互 → 提交补丁得到奖励 → 更新策略。对外评测另走 Multi-SWE-bench 或 SWE-bench 的 harness。

### 变体

按语言和仓库切开。新增批次会改变训练分布，实验要锁定数据快照。

### 和 SWE-bench 的差异

它是多语言训练场。不要把它的训练奖励写成 Multi-SWE-bench 榜的分数。

## SWT-bench

### 它问的问题

把 SWE-bench 的输入输出对调。给定仓库和 issue，模型交的不是修复，而是一个能复现问题的测试：在修复前失败，在金补丁打上之后通过，并且不把原有测试打坏。

### 一道题的字段，以及谁能看见

| 字段 | 是什么 | 解题时 | 评测时 |
| --- | --- | --- | --- |
| issue 与 `base_commit` | 与 SWE-bench 相同 | 可见 | 容器起点 |
| 金修复补丁 | 人类 PR 的非测试改动 | 不可见 | 用来判断新测试是否「修了就过」 |
| 金测试 | 人类 PR 里的测试 | 不可见 | 用来算覆盖率差距，不是让模型去抄 |
| 模型交的测试补丁或脚本 | 预测文件的内容 | 模型自己的输出 | 被打进仓库或单独执行 |

切分从 SWE-bench 过滤而来。`[核对]` 仓库表格写 Lite 276、Verified 433、Full 与 SWE-bench 全集同量级。金测试在这些切分上的适用性和覆盖率要随表引用，不要假设每道 SWE-bench 题都能直接当 SWT 题。

### 标签怎样造出来

成功的定义是行为，不是和金测试文本相同。一道生成测试算成功，当它在原代码上失败、在金修复上通过，且不引起原有测试失败。覆盖率是附加指标：生成测试覆盖到的、金测试也覆盖到的行，两者的差距。算覆盖率差距时，同一次评测目录里要有金测试的结果。

### 评测 harness 的流程

默认是单元测试模式：把模型的改动当成测试套件的一部分，跑受影响的测试，看是否新增了失败到通过、且没有弄坏已有测试。

另一种是复现脚本模式：预测是一段独立脚本。在原代码上应以失败退出，在金修复上应以成功退出。这个模式不跑整套单元测试。

两种模式的分数不能平均在一起。harness 从 SWE-bench 的 Docker 评测改来，预测 JSONL 的语义从「修复补丁」换成「测试补丁」。

### 解题时的工具

可以是一次生成，也可以是 OpenHands 这类会跑代码的 agent。无论哪种，金修复和金测试都不在提示里。agent 可以跑仓库里已有的测试，那不等于看见了判分用的金测试。

### 端到端时序

用 SWE-bench 实例当底。解题阶段只给 issue 和旧代码。打分阶段把模型测试和金修复组合起来跑两遍（修前、修后），再可选地和金测试比覆盖率。

### 变体

Lite、Verified、Full；单元测试模式与脚本模式；成功率与覆盖率差距。

### 和 SWE-bench 的差异

提交物反了。SWE-bench 隐藏的是测试、公开的是让你写修复。SWT-bench 隐藏的是金修复和金测试、公开的是让你写测试。一个模型 SWE-bench 高，不说明它会写复现测试。

## SWE-Lancer

### 它问的问题

用 Upwork 上真实付过钱的自由职业任务，看模型能完成多少工程工作，并把通过的任务按真实报酬加总。任务集中在 Expensify 这一类真实产品仓库，而不是 12 个 Python 库。

有两类题。独立贡献者题：自己改代码实现 bug 修复或功能。管理者题：阅读几种实现提案，选出应被采纳的那一种。

### 一道题的字段，以及谁能看见

| 字段 | 是什么 | 解题时 | 评测时 |
| --- | --- | --- | --- |
| 标题与描述 | 外包任务原文 | 可见 | 不做文本匹配 |
| 报酬 | 当时付给自由职业者的金额 | 可以可见，但是难度标签不是测试 | 通过后计入金额 |
| 变体 | 独立贡献者或管理者 | 可见 | 决定判分分支 |
| 代码快照 | 问题修复前的产品仓库 | 可见 | 容器起点 |
| 提案列表 | 只在管理者题 | 可见 | 与被录用的选择比对 |
| 端到端测试 | 工程师三次复核过的浏览器测试 | 不可见 | 独立贡献者题的判分 |
| 管理者的真实选择 | 当时被雇用来做决定的人的选择 | 不可见 | 管理者题的标准答案 |

`[核对]` 论文全集约 1488 题、报酬合计约一百万美元。公开的 Diamond 切分更小。2025 年 7 月的离线复现包把需要联网的题拿掉之后，独立贡献者题大约 198 道，并说明这是从论文里更大的一组里删掉无法离线稳定运行的题。金额区间以论文为准，不要和后来的子集混用。

### 标签怎样造出来

任务和金额来自真实成交，不是模型估的价。独立贡献者题的正确性由端到端测试定义，测试经过多名工程师复核，因为产品行为往往无法被一个单元测试说完。管理者题的标准答案是当时被采纳的提案，不是「任意说得通的提案」。

### 评测 harness 的流程

统一 Docker 镜像。独立贡献者：agent 改仓库，然后跑该题的端到端测试（Playwright 一类，驱动真实界面流程）。通过则拿到该题金额，否则为 0。管理者：模型输出选项，与标准答案一致则得分。

后来的离线包去掉了运行时上网，以减少网络抖动造成的假失败。自检可以用空操作（应当失败）和打上金解（应当通过）。

指标至少有三个：任务准确率、赚到的金额、通过与失败的题数。金额不是准确率的别名。一道 3 万美元的题和一道 50 美元的题在金额指标里权重差很多。

### 解题时的工具

独立贡献者题需要能改代码、跑构建，并可能要使用「用户工具」在界面里点选，以便复现流程。这和 SWE-bench 只交 diff、由 harness 跑单元测试不同。管理者题可以是读提案后一次选择，不一定有编辑循环。论文和后续 solver 都把工具写在实验配置里，引用时要写是 Dummy、简单多步 agent，还是带用户工具。

### 端到端时序

从成交任务和修复前快照造题 → 为独立贡献者题写并复核端到端测试 → agent 在镜像里工作 → 测试或选项比对 → 汇总准确率和金额。

### 变体

全集与 Diamond；独立贡献者与管理者；需要联网的原版与离线子集。三种不要写成一个百分数。

### 和 SWE-bench 的差异

判分可以是浏览器里的用户流程，而不只是单元测试的失败到通过。多了一个「选提案」题型。主指标可以是钱，而不是题数比例。仓库是产品应用，不是库。

## SWE-PolyBench

### 它问的问题

多语言的仓库级 issue resolving，并同时报告「测试过了没有」和「改到了没有金补丁碰到的那些代码节点」。语言为 Java、JavaScript、TypeScript、Python。

### 一道题的字段，以及谁能看见

预测文件至少要有 `instance_id` 和字符串形式的 `model_patch`。解题可见 issue 和起点代码。评测使用隐藏测试，以及从金补丁抽出的文件和语法节点，后者只用于定位指标，不给模型。

`[核对]` 完整集约 2110。另有分层的 500 题子集，以及约 382 题的 verified 子集。以仓库为准。

### 标签怎样造出来

从多语言仓库的 issue 与 PR 中筛选可运行样本，按难度或改动形态分层，避免榜单被某一类简单 Python 题占满。节点标签来自对金补丁的程序分析（文件，以及更细的语法树节点），用来衡量定位，不用来要求 diff 相同。

### 评测 harness 的流程

`run_evaluation.py` 读预测、数据集和结果目录。默认既算测试通过（resolved），也算检索指标。可以只重算文件级指标，也可以额外算节点级精确率和召回，后者更慢。金补丁模式用来检查环境和指标脚本。实例结果里会留下通过与失败的测试列表，汇总进结果文件。

### 解题时的工具

不绑定 scaffold。定位指标允许你分析「模型改对了文件但测试没过」或「测试过了但改在别的地方」。工具如果强行把金补丁文件喂给模型，定位指标就失效，这种设定必须叫 oracle，不能混进主结果。

### 端到端时序

与 SWE-bench 相同的解题和打分，再加上一轮对补丁位置的静态比较。静态比较不代替测试。

### 变体

全量、500、verified。指标：通过率、文件级精确率/召回、节点级精确率/召回。

### 和 SWE-bench 的差异

多了定位指标和多语言分层子集。resolved 的含义仍然是测试，不是节点全部命中。

## OmniGIRL

### 它问的问题

issue resolving，但问题陈述可以同时包含文本和图片，仓库也不限于 Python。用来看「只读文字的 scaffold」会漏掉什么。

### 一道题的字段，以及谁能看见

解题可见：issue 文本和其中的截图或界面图片，以及起点代码。不可见：测试补丁和金补丁。提交物是 `model_patch`。预构建 Docker 用来保证测试环境一致。`[核对]` 语言构成和题数以论文及数据集卡为准。

### 标签怎样造出来

用自动管线（作者称为 SWE-Factory）从仓库构造可运行的 issue 样本：装环境、确认测试过渡、保留带有图像信息的 issue。图像是问题的一部分，不是装饰。

### 评测 harness 的流程

与 SWE-bench 同型：JSONL 补丁、并行 worker、`run_id`、在 amd64 上跑官方镜像、报告写到 harness 的 reports 目录。判分看测试是否解决，不看模型有没有「描述对图片」。

### 解题时的工具

若 scaffold 不能读图，它看到的题目是残缺的，这个分数不能和多模态 agent 比。文本工具仍是搜索、编辑、执行；图像输入是提示的一部分，不是评测脚本的一部分。

### 端到端时序

自动造环境 → 模型在看见图片的条件下改代码 → 干净容器打补丁并跑测试。

### 变体

按语言、按是否含图切开。不含图的子集不能代表整个 OmniGIRL。

### 和 SWE-bench 的差异

和 SWE-bench Multimodal 同属「问题里有图」。不要合并题库。OmniGIRL 强调自动造题管线和多语言；官方 Multimodal 是 SWE-bench 站点上的另一套切片。

## DevEval

### 它问的问题

在真实仓库里，按自然语言需求生成一段新代码，而不是修复一个 issue。生成结果要能通过该样本的测试，并且最好用上仓库里已经存在的依赖。

### 一道题的字段，以及谁能看见

| 字段 | 是什么 | 解题时 | 评测时 |
| --- | --- | --- | --- |
| 需求说明 | 人工标注的自然语言 | 可见 | 不参与匹配 |
| 目标文件与插入位置 | 要填的函数或代码块在仓库中的位置 | 可见 | 用来把生成结果填回去 |
| 上下文设定 | 无上下文、仅本文件，或更大的仓库上下文 | 由实验协议决定可见范围 | 必须和协议一致 |
| 参考实现与参考依赖 | 人写的原实现、以及它调用了哪些项目内符号 | 不可见 | 依赖召回用；功能对错不靠文本相等 |
| 测试 | 仓库测试 | 不可见 | 填回代码后执行 |

`[核对]` 约 1825 个样本、100 余个仓库、十余个主题。以论文为准。

### 标签怎样造出来

从真实仓库里抽可被测试覆盖的实现单元，人工写需求，并标出参考依赖。对齐的是仓库里的代码分布和依赖分布，不是竞赛题的输入输出分布。

### 评测 harness 的流程

对每个样本找到目标文件和位置，用生成代码替换该位置，跑测试，再把文件恢复，以便下一题。功能指标是无偏的 pass@k：每题采样 n 份，其中 c 份通过测试，再估算 pass@k。

第二个指标是参考依赖的 recall@k：生成代码有没有调用到标注的那些项目内依赖。测试全过但完全不用仓库已有函数，在这个指标上仍然是差的。

### 解题时的工具

主协议是按上下文档位生成，不是自由 agent。上下文档位本身就是「工具」：无上下文、本文件、本文件加上文。若改成 agent 自己搜仓库，必须单列，不能和「只给本文件」的 pass@k 比较。

### 端到端时序

标注需求 → 按档位把上下文给模型 → 填回仓库 → 跑测试并计算依赖召回 → 恢复现场。

### 变体

三种上下文档位。pass@k 与 recall@k 都要报。贪心解码和温度采样分开。

### 和 SWE-bench 的差异

DevEval 生成新代码，SWE-bench 修改旧代码以关闭 issue。DevEval 的提交物是填进某个位置的片段，不是一份可以 `git apply` 的修复补丁。两个指标里，只有 pass@k 对应「行为对不对」。

## RepoBench

### 它问的问题

在仓库规模的上下文里做代码补全，并单独衡量「能不能把跨文件的相关片段找出来」。它不要求交一个能通过测试的补丁。

### 一道题的字段，以及谁能看见

补全题：光标前的代码、可选的跨文件上下文、需要补上的后文。检索题：给定当前位置，候选的其他文件片段，其中有标注为相关的金片段。金片段在检索评测里是标签；若协议规定模型自己检索，则不能预先把金片段放进提示。

### 标签怎样造出来

从真实仓库的后续代码切出补全目标，并把目标真正引用到的跨文件代码当作检索金标准。切分时要避开用「答案后文」泄漏提示。

### 评测 harness 的流程

检索：算精确率、召回或排序指标。补全：精确匹配、编辑相似度，以及有的设定下的 CodeBLEU。没有统一的 Docker 测试通过率。所以「更高的编辑相似度」不等于「仓库还能跑」。

### 解题时的工具

标准设定是一次补全。检索可以是独立模块（BM25 或模型），再把取回的片段拼进提示。这和 agent 的多步编辑不是同一协议。

### 端到端时序

切仓库快照 → 构造光标位置 → 检索或直接给上下文 → 生成补全 → 与后文做文本指标。

### 变体

检索任务与补全任务分开。语言以论文中的 Python 与 Java 为主。`[核对]` 子任务名称以所用论文版本为准。

### 和 SWE-bench 的差异

没有 issue，没有 FAIL_TO_PASS，提交物是续写而不是补丁。它可以解释「上下文找得准不准」，不能代替「bug 修没修好」。

## CrossCodeEval

### 它问的问题

跨文件的代码补全，而且目标语言不只有 Python。用来衡量模型在光标处是否真的用到了别的文件里的定义，而不是只靠本文件的统计模式。

### 一道题的字段，以及谁能看见

本文件光标前的前缀、跨文件上下文（按协议给或由检索提供）、应当补全的片段。语言标签包括 Python、Java、TypeScript、C#。`[核对]` 以论文的语言列表为准。金跨文件上下文在「oracle 上下文」设定里可见，在「检索设定」里不可见。

### 标签怎样造出来

选取必须依赖跨文件信息才能确定的补全点，减少「只看本文件就能猜中」的题。金上下文来自静态分析得到的相关片段。

### 评测 harness 的流程

生成补全后计算：精确匹配、标识符匹配、编辑相似度。标识符匹配专门看有没有写出跨文件里的那些名字。不执行仓库测试。

### 解题时的工具

无 agent 循环。实验变量是上下文从哪来：空、检索、或 oracle。oracle 是上限，不是真实使用方式。

### 端到端时序

静态分析造题 → 按设定填上下文 → 一次生成 → 文本指标。

### 变体

按语言、按上下文设定。各语言的分不能合成一个「代码能力」。

### 和 SWE-bench 的差异

与 RepoBench 同属补全考试，和 SWE-bench 的差别也相同：文本相似不是行为正确。和 RepoBench 之间也不要合并，CrossCodeEval 的重点是跨语言和「非看本文件就能猜中」的过滤。

## HumanEval

### 它问的问题

给一个 Python 函数的签名和文档字符串，写出函数体，使隐藏单元测试通过。164 道手工题。这是函数级考试，用来说明后来的仓库级考试在补什么，不宜再单独支撑前沿模型的比较。

### 一道题的字段，以及谁能看见

| 字段 | 解题时 | 评测时 |
| --- | --- | --- |
| 函数签名与文档字符串，文档里可能含少量例子 | 可见 | 作为程序的前半段 |
| 隐藏单元测试 | 不可见 | 执行 |
| 参考实现 | 不可见 | 不要求文本相同 |

### 标签怎样造出来

人工编写函数说明和测试。测试数量不多，后来暴露出「测试太少，错误实现也能通过」的问题，因此才有 HumanEval+。

### 评测 harness 的流程

把模型生成的函数体和隐藏测试拼成程序，在沙箱里执行。每题采样 n 次，用无偏 pass@k 估计「k 次里至少一次全对」的概率。不能把 n 次里的最高分假装成一次生成的分数。

### 解题时的工具

没有。一次采样。若加上自我修复循环，要写成另一个协议。

### 端到端时序

写题和测试 → 采样 → 执行 → pass@k。

### 变体

原始 HumanEval 与 EvalPlus 的 HumanEval+（测试更多、更严）。两者的 pass@1 不能写成同一个 HumanEval。

### 和 SWE-bench 的差异

一道函数、一组短测试、无仓库、无工具。饱和之后，分数差异更多来自测试集被背下来，而不是工程能力。

## MBPP

### 它问的问题

根据一句简短的 Python 编程说明写出函数。题目比 HumanEval 更偏基础，规模更大。常被一起引用，但不是同一套题。

### 一道题的字段，以及谁能看见

题面描述可见。一部分协议会把一两则公开测试放进提示，隐藏测试仍不可见。参考解不可见。`[核对]` 全集约 974，清洗后的测试集常被说成约 500。写清用的是哪一版。

### 标签怎样造出来

众包短题，每题带若干断言。清洗版去掉了题面含糊或测试不可靠的样本。EvalPlus 的 MBPP+ 加严测试。

### 评测 harness 的流程

与 HumanEval 相同：拼接、沙箱执行、pass@k。提示里如果包含了公开测试，模型可以针对这些例子编写，隐藏测试才是泛化。

### 解题时的工具

没有。一次生成。

### 端到端时序

与 HumanEval 相同。

### 变体

原版、sanitized、MBPP+。few-shot 提示里放哪些例子也要固定，否则不是同一考试。

### 和 SWE-bench 的差异

与 HumanEval 相同，并且更基础。MBPP 高只说明短函数生成还行。

## MLE-bench

### 它问的问题

让 agent 在真实的 Kaggle 竞赛设定里做机器学习工程：读说明、用训练数据做模型、交出一份符合格式的 CSV。考的是整段实验流程，不是修一个函数。

### 一道题的字段，以及谁能看见

| 字段 | 解题时 | 评测时 |
| --- | --- | --- |
| 竞赛说明、数据文件、样例提交 | 可见 | 说明不参与打分 |
| 本地准备的答案与分级脚本 | 不可见 | 按该竞赛的指标算分 |
| 奖牌阈值 | 不可见 | 由公开排行榜的规则换算 |
| 提交 CSV | 模型的产物 | 唯一被打分的文件 |

`[核对]` 75 场竞赛。复杂度有低、中、高。官方建议的比较配置包括约 24 小时、固定 CPU 内存和一块 GPU，并至少三个种子。偏离这些要写明。

### 标签怎样造出来

选用允许离线复现的竞赛，准备与私有排行榜可比的本地答案切分，并为每场竞赛实现它自己的指标（AUC、特殊损失等）。奖牌线按 Kaggle 的队伍规模规则换算，使「铜牌」在不同竞赛里大致表示同样的相对名次。阈值是标签的一部分，不是模型自己定的。

### 评测 harness 的流程

1. 给 agent 一个只含训练材料和说明的环境。
2. agent 在时长和算力上限内训练、调试、写文件。
3. 收集 `submission.csv`。没有文件，或格式不合法，则该次没有有效提交。
4. 本地 grader 算指标，再对照铜、银、金和中位数阈值。
5. 主指标是 Any Medal：达到铜牌或更好的尝试所占比例。同时报告有效提交率、高于中位数的比例、金银铜分开的数。
6. 多次尝试可以用 pass@k：k 次里至少一次拿到奖牌。这和「单次奖牌率」必须分开。

### 解题时的工具

由 agent 提供。公开比较里，同一模型配 AIDE、OpenHands 或 MLAB，奖牌率差一截。AIDE 一类专门做实验搜索的 scaffold 不是竞赛说明的一部分。agent 可以跑训练、看验证集，但不能看见本地私有答案。

### 端到端时序

准备竞赛包和本地答案 → agent 长时间实验 → 交出 CSV → 本地打分 → 对照奖牌线。打分不看代码是否优雅，只看提交文件。

### 变体

全量与 lite；低中高复杂度；单次与 pass@k；不同时长（有实验把 24 小时加长，分数会继续变）。

### 和 SWE-bench 的差异

提交物是预测表，不是 diff。成功是相对人类排行榜的名次，不是全部测试变绿。时长以小时计，scaffold 对分数的影响可以被单独测量。随机种子必须报告。

## PaperBench

### 它问的问题

给一篇机器学习论文，让 agent 把论文里的方法复现出来：写出代码、跑通实验、得到与论文相符的结果。时程和开放度都高于修一个 issue。

### 一道题的字段，以及谁能看见

| 字段 | 解题时 | 评测时 |
| --- | --- | --- |
| 论文 PDF 与转写的正文 | 可见 | 法官对照的对象 |
| 附录式澄清（addendum） | 可见 | 缩小允许的实现范围 |
| 黑名单 | 可见，列出不许访问的资料 | 用来判断是否违规取巧 |
| 分层评分表 | 不可见 | 法官逐条打 0/1 |
| 复现仓库与 `reproduce.sh` | 模型的产物 | 执行类条目要真的跑 |

题目来自 ICML 2024 一类会议论文，评分表与论文作者一起写过。`[核对]` 论文篇数以 OpenAI 的 PaperBench 发布为准。

### 标签怎样造出来

把论文拆成树状要求：代码是否实现了某个算法、代码是否执行成功、结果是否与论文一致。叶子是二元的。父节点是子节点的加权平均，根节点是 0 到 1 的复现分。这是人写的评分表，不是单元测试名。

### 评测 harness 的流程

agent 在沙箱里开发。结束后，用一个法官模型按评分表看仓库、执行记录和结果。法官本身是协议的一部分：换法官模型，分数不一定保持。执行类条目要求 `reproduce.sh` 真的跑过，不能只看代码像不像。评分表不放在 agent 能读到的目录里。

### 解题时的工具

需要 shell、编辑器和长时间运行。公开环境里，中间步骤的奖励是 0，只有提交时才按评分表给连续分。禁止访问黑名单上的现成实现。若 scaffold 允许上网，必须说明黑名单如何强制，否则分数不可比。

### 端到端时序

与作者一起写评分表 → agent 按论文复现 → 法官自底向上打分 → 报告根分数，最好同时报告三类叶子（实现、执行、结果）分别得了多少。

### 变体

不同论文、不同法官、是否允许部分复现。根分数会掩盖「代码写了但没跑」。

### 和 SWE-bench 的差异

没有 FAIL_TO_PASS。正确性由评分表和法官决定，带有法官误差。提交物是整个复现仓库，不是一份补丁。一道题的时长和自由度都更大。

## OSWorld

### 它问的问题

在真实的桌面操作系统里完成任务：改系统设置、用办公软件、在浏览器里操作。它不是 coding exam 的主榜，放进来是为了把「有环境、有执行奖励的 agent」和「交补丁的 coding agent」分开。

### 一道题的字段，以及谁能看见

指令可见。虚拟机初始快照可见（作为起始桌面）。任务配置里的评测脚本和期望文件不可见。模型每步通常能看到截图，有的设定还有辅助功能树。`[核对]` 原始发布约数百道任务，覆盖 Ubuntu 与 Windows 等。以所用版本为准。

### 标签怎样造出来

人工设计初始状态、指令和检查脚本。检查脚本查看文件内容、界面状态或应用数据，而不是看点击轨迹是否和示范相同。

### 评测 harness 的流程

启动快照 → agent 多步发出键鼠动作 → 超时或模型宣布结束 → 在虚拟机里跑该题的奖励脚本 → 得到成功或失败，有的题有部分分。不看轨迹文本相不相等。

### 解题时的工具

动作空间是鼠标、键盘，以及有的实现里的辅助功能 API。这不是 bash，也不是 `git apply`。把 OSWorld 的通过率拿去和 SWE-bench resolved 排名，没有意义。

### 端到端时序

造快照和检查脚本 → 交互 → 脚本打分。现场就是那台虚拟机，和 Terminal-Bench 一样不能只交一个 diff。

### 变体

操作系统、是否提供辅助功能树、纯截图。应用类别（浏览器、办公、系统）应分开看。

### 和 SWE-bench 的差异

观察是屏幕，动作是键鼠，奖励是环境脚本。和 Terminal-Bench 的差别是图形界面，而不是 shell。它和交补丁的 coding benchmark 不是同一类任务。
